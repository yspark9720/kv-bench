# Week11 평가 보완 사전 계획 (2026-11-12)

사용자가 제공한 「kv-bench 평가 방식 점검」을 반영한다. 기존 7,290회 결과는 보존하고 별도 추가 평가로 구분한다. 아래 격자·seed·예시 SLO는 추가 결과를 보기 전에 정한다.

## 확인할 질문

1. 넉넉한 메모리에서 같은 계산/FIFO 모델을 실행한 참조값과 기존 정책의 격차는 얼마인가?
2. 평균으로 가렸던 조건·도착률별 정책 순위가 PCIe/CPU 축에서 바뀌는가?
3. 900초 실행과 300초 warm-up에서도 짧은 실행의 결론이 유지되는가?
4. prefill 속도 가정을 바꾸면 정책의 순위와 비제약 참조값이 어떻게 변하는가?
5. 예시 절대 지연·완료 기준을 만족하는 최대 **시험 격자점**은 어디인가?

## 실행 격자

- 비제약 참조: 기존 3설정 × 9조건 × seed 0–14, `pin_all`, GPU KV 64GiB. GPU 최대 수요가 용량보다 작고 거절이 없는지 검증한다. 계산/FIFO는 동일하므로 이론적 최적 하한이라고 부르지 않는다.
- 환경 축: 180s/stress 0.2 및 0.3, `base_4x`와 `both_4x`, seed 0–4. 네 block 정책을 같은 trace에서 비교한다.
  - PCIe: 12 / 3 / 1.5 / 0.9 / 0.6 / 0.3 GB/s, CPU 64GiB.
  - CPU: 64 / 8 / 4 / 2 / 1 / 0.5 GiB, PCIe 12GB/s. 중복 기본 환경은 한 번만 실행한다.
- 긴 실행: 900초, warm-up 300초. 같은 두 조건과 도착률 0.2/0.3. seed 0–4, PCIe 12 / 1.5 / 0.9 GB/s, CPU 64GiB. 비제약 참조도 실행한다.
- 용량 격자: 긴 실행의 `both_4x`에 도착률 0.1/0.4를 추가해 0.1/0.2/0.3/0.4 세션/s를 비교한다. PCIe 12 및 0.9GB/s의 절대 지연 곡선을 읽는다.
- prefill 가정 민감도: 180s/stress 0.2, 두 조건, seed 0–4, 8,000 / 4,000 / 2,000 tokens/s, 기본 PCIe/CPU, 네 block 정책과 비제약 참조. 실제 GPU의 보정값이라고 해석하지 않는다.

CPU를 쓰지 않는 두 정책은 같은 trace·prefill에서 PCIe/CPU 변경의 영향을 받지 않는다. 한 번 실행한 결과를 환경 행에 재사용하되, 실제 replay 수와 분석 행 수를 구분하고 원본 요청 hash를 기록한다. 이는 독립 표본을 늘리는 작업이 아니다.

## 지표와 판정

- 주 지표: 실제 도구 종료부터 첫 토큰까지의 복귀 P95, 비제약 참조 대비 지연 격차(ms), 완료율/거절률. 일반 TTFT는 보조로 함께 보고한다.
- 짧은 실행과의 직접 비교에는 기존과 같은 세션 최초 도착 cohort를 사용한다. 긴 실행의 시간 구간 비교에는 실제 도구 종료가 측정 구간에 속하는 복귀를 사용하고 두 분모를 구분한다.
- prefill/PCIe 사용률은 `[warm-up, 외부 도착 종료)`와 서비스 예약 구간의 겹침으로 계산한다. drain을 포함한 기존 사용률도 별도 보존한다.
- CPU 최고 사용량, GPU 수요/4GiB 비율, CPU admission 허용·거절 사유와 교체 횟수로 정책의 실제 작동 여부를 확인한다.
- 긴 실행의 `[300,600)`, `[600,900)`를 별도로 보고해 잔여 변화가 큰지 확인한다. 긴 실행만으로 정상 상태를 달성했다고 단정하지 않는다.
- 짝차이 95% CI는 조건을 섞지 않고 seed 단위 bootstrap 2,000회로 계산한다. seed 5개와 복수 비교의 한계를 명시한다.
- 용량의 **예시 기준**: normal P95와 복귀 P95가 각각 500ms 이하 또는 각각 1,000ms 이하인 두 profile, cohort stress 완료율 ≥99%, normal 거절률 ≤1%. 이는 사용자가 정한 서비스 SLO나 실제 시스템의 용량이 아니다. 모든 seed가 기준을 통과한 최대 시험 도착률, seed 통과 수, 상위 격자 미시험 여부와 비단조 결과를 함께 표시한다. 격자 밖 한계는 보간·외삽하지 않는다.

## 보존 및 검증

- 엔진·기존 생성기·정책 판단을 바꾸지 않는다. 추가 관측기는 서비스 예약/로그/CPU 사용량을 관측하며, 일반 replay와 요청·점유율·기존 지표가 동일한지 테스트한다.
- 추가 스크립트·설정·seed·입력 hash·실행 수·결과 hash를 manifest에 남긴다. 원래 데이터 및 평가 source hash를 다시 검증한다.
- 외부 검토의 임시 폴더 결과는 이번 저장소에서 재실행한 결과와 구분한다. 재실행하지 않은 수치를 검증 완료라고 인용하지 않는다.

## 이번 수정에 포함하지 않는 검증

배정 서버의 실측, 실제 서빙 엔진 검증, 공유 prefix와 미복귀 생명주기 모델은 수행하지 않는다. 현재 trace는 중간 도구 호출 뒤 반드시 복귀하므로, 미래 재사용의 불확실성·공유 prefix를 대상으로 한 원 논문 전체를 평가했다고 표현하지 않는다. 단순히 턴 수를 줄이면 마지막 턴에서 즉시 해제되어 미복귀 KV가 남는 상황을 재현하지 못하므로 그런 입력 변형을 대체 검증으로 쓰지 않는다.
