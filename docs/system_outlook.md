# 결론과 시스템 연결 (전망)

작성 2026-10-29 · 전규빈. 이 프로젝트의 분석 결과를 실제 서빙 시스템에 어떻게 붙일 수 있는지 정리한다. **이번 학기 범위는 시뮬레이터이고, 실제 연동은 구현하지 않았다.** 아래는 지금 결과와 코드가 이미 갖춘 것에서 출발한 연결 방향이다.

## 1. 분석에서 얻은 것

1. **기존 정책이 실패하는 원인**: 도구 대기 중인 KV 를 언제 지우거나 옮길지만 정하는 정책으로는 메모리 여유(최고 점유율)를 지킬 수 없다. Peak 는 새 요청이 입장하는 순간에 생긴다([10주차 실험](week10_experiment.md)).
2. **입장 제어 + 미리 옮기기**: 입장 상한을 두고 넘을 때만 오래 기다린 세션을 CPU 로 옮기면, 재계산 없이 같은 SLO 를 지키고 일반 요청 TTFT 는 Evict 의 절반이다. 상한만 두고 옮기지 않으면 무너진다(대조군).
3. **비용이 누구에게 가는가**: 재계산은 공유 prefill 을 써서 비용이 다른 사용자에게 넘어가고, offload 는 별도 PCIe 를 써서 비용이 세션 안에 머문다. PCIe 를 8배 느리게, CPU 풀을 64배 작게 해도 유지된다([민감도](week10_sensitivity.md)).

## 2. 설명 가능한 메모리 관리

시뮬레이터는 모든 결정을 이유와 비용과 함께 기록한다(`events.csv`). 180초 · 0.2 · both_4x · seed 1 의 Watermark Offload 실제 기록:

```text
130634.7 ms  ARRIVE         stress-000021  새 도구 세션 도착
130634.7 ms  OFFLOAD_START  stress-000013  424 MB, reason=pressure   ← 그대로 받으면 90% 초과 → 가장 오래 기다린 세션을 CPU 로
130681.8 ms  OFFLOAD_DONE   stress-000013
130681.8 ms  ADMIT          stress-000021  +252 blocks, wait 47.1 ms ← 자리가 나자 입장
```

이 기록만으로 운영자는 다음을 바로 답할 수 있다.

| 질문 | 기록에서 읽는 것 |
|---|---|
| 이 요청은 왜 기다렸나 / 거절됐나 | 도착 시 점유율, 상한, 그 시점에 블록을 쥐고 있던 idle 세션 |
| 누구의 메모리를 비웠나, 왜 그 세션인가 | 회수 대상, 사유(idle · pressure · ttl), idle 시간 |
| 그 결정의 비용은 | 전송 바이트 · 시간, 재계산 토큰, 입장 대기 |
| 다른 정책이었다면 | 같은 트레이스를 정책만 바꿔 재생(반사실) — 7주차 `explain_rejects.py` 의 방식 |

## 3. 실제 시스템에 붙이는 구조

정책은 엔진 상태를 직접 바꾸지 않고 네 지점에서만 결정한다. 이 경계가 그대로 실제 서빙 엔진의 확장 지점에 대응된다.

| 시뮬레이터의 결정 지점 | 결정 | 실제 시스템에서 붙일 곳 (방향) |
|---|---|---|
| `on_idle_start` | 도구 대기 시작 시 유지 · 옮김 · 삭제 | 에이전트 프레임워크가 "도구 호출 시작"을 서빙 엔진에 알리는 지점 |
| `on_ttl_expire` | 유지 시간이 끝났을 때 | 엔진 스케줄러의 타이머 |
| `select_victims` | 자리가 모자랄 때 누구를 비울지 | vLLM 스케줄러의 preemption(recompute / swap) 선택, LMCache 같은 KV 오프로드 연결부 |
| `admission_ceiling` | 몇 % 까지 새 요청을 받을지 | 스케줄러의 입장 판단(현재 엔진들은 메모리 한도까지 받는다) |

연동하면 다음이 가능해진다.

- **유연한 정책 변경**: 정책 파일 하나를 바꿔 끼우듯 운영 중에 정책과 상한을 바꾼다. 측정한 PCIe 속도 · prefill 처리량 · CPU 여유로 "옮길지 지울지"를 고르는 규칙은 민감도 실험의 결과(재계산 비용이 공유 자원에 걸리는가)에서 바로 나온다.
- **원인 파악이 쉬운 운영**: 모든 결정이 이유 · 비용과 함께 남으므로, 지연이나 거절이 생겼을 때 "메모리 부족" 대신 "어느 세션이 무엇을 기다리며 쥐고 있었고, 어떤 정책이면 피했는지"를 바로 보여 준다.
- **사전 검증**: 실제 서빙 로그를 트레이스로 바꿔 시뮬레이터에 넣으면, 정책을 바꾸기 전에 같은 부하에서의 결과를 먼저 확인할 수 있다.

## 4. 남은 과제

- 실제 GPU 에서 prefill · decode · PCIe 속도 측정과, prefill 배치(chunked prefill)를 반영한 재계산 비용 재확인
- 도구 대기 길이 예측기(지금은 트레이스의 실제 값을 쓰는 단순화)
- 서빙 엔진 스케줄러에 결정 지점 네 개를 연결하는 프로토타입
