# 10주차 계획: 입장 상한 Offload (실험 전 확정본)

작성 2026-10-29 · 전규빈. **실험을 돌리기 전에** 목표 · 가설 · 정책 규칙 · 실험 · 판정 기준을 먼저 고정한 문서다. 결과를 본 뒤 이 문서의 기준을 바꾸지 않는다. 바꿀 일이 생기면 별도 절에 이유와 함께 남긴다.

## 1. 목표와 위치

프로젝트 목표: 도구 대기가 길어지는 부하에서 KV Cache 관리 정책이 정상 사용자의 SLO 를 어디까지 지키는지 밝히고, 그 결과로 SLO 를 지키는 정책을 제시한다.

이 문서는 그중 **"결과로 더 나은 정책을 만들 수 있는가"** 에 해당한다. 7주차 결론(점유율 90 % 를 지키며 재계산을 줄이는 정책이 필요)과 9주차 관찰(Duration-Aware 도 순간 Peak 를 놓침)이 같은 지점을 가리킨다.

## 2. 관찰 → 원인 → 가설

**관찰 (9주차).** LRU Offload 와 Duration-Aware 는 재계산 없이 normal TTFT 를 낮게 유지하지만, 최고 점유율 90 % 기준에서 떨어진다. 9주차 사례 분석에서 Peak 는 offload 가 끝난 직후의 stress ADMIT 에서 생겼다.

**원인 (코드).** 엔진은 블록이 100 % 찰 때까지 입장을 허용하고(`GpuPool.can_alloc`), 정책의 회수(`select_victims`)도 블록이 모자랄 때만 호출된다. 따라서 idle 진입 시점의 결정(KEEP / OFFLOAD / EVICT)만으로는 **입장이 만드는 Peak** 를 막을 수 없다. 90 % 는 평가 목표인데 엔진에는 그 목표를 지키는 장치가 없다.

**가설 H.** 입장 상한을 90 % 로 두고, 상한을 넘을 입장이 있으면 가장 오래 기다린 idle 세션부터 CPU 로 옮겨 자리를 만들면

- H-a. 최고 점유율 90 % 를 지키면서(상한이므로 구조상 보장),
- H-b. normal P95 TTFT 와 거절률은 LRU Offload 와 비슷하게 유지되고,
- H-c. 재계산은 0 이며, 대가는 전송량 증가와 짧은 입장 대기다.

**대조 가설.** 회수 없이 상한만 두면(Pin-All + 상한) 입장 대기가 길어져 TTFT · 거절이 나빠진다. → H-b 가 성립한다면 그 이유는 상한 자체가 아니라 **상한 + 회수의 조합** 때문임을 보인다.

H-a 는 정의상 성립하므로 이 실험이 검증하는 것은 H-b · H-c, 즉 **90 % 여유를 강제할 때 치르는 비용**이다.

## 3. 정책 규칙

| 이름 | idle 진입 | 입장 상한 | 상한 초과 입장 시 |
|---|---|---|---|
| `watermark_offload` (제안) | 유지 (KEEP) | 전체 블록의 90 % | 가장 오래 idle 인 세션부터 CPU 로 offload 해 상한 안으로. offload 가 끝나 블록이 풀리면 입장. CPU 가 차면 evict |
| `pin_all_capped` (대조) | 유지 (KEEP) | 전체 블록의 90 % | 회수 없음. 자리가 날 때까지 대기, 30 s 넘으면 거절 |

- 상한은 엔진의 입장 판단에만 쓰인다: 입장 후 사용 블록이 `floor(0.9 × 전체)` 를 넘지 않을 때만 받는다. 기존 정책은 상한 1.0 (= 지금과 동일)이다.
- 입장 시 턴 종료까지의 블록을 한 번에 예약하므로, 상한 아래로 입장한 세션이 나중에 블록을 더 늘리지 않는다. offload 중인 블록은 전송이 끝날 때까지 사용 중으로 센다.
- 상한 값 0.9 는 SLO 기준(최고 점유율 ≤ 90 %)에서 왔고, 실험 중에 조정하지 않는다.

## 4. 실험 (고정)

| 항목 | 값 | 근거 |
|---|---|---|
| 워크로드 · 조건 | 9주차 `w2-factorial` 9조건 (w0_1x, base · burst · wait · both × 2 · 4x) | 9주차와 같은 입력으로 비교 |
| 설정 | 60 s · 0.2 / 180 s · 0.2 / 180 s · 0.3 (9주차 config 그대로) | 180 s · 0.2 를 주 결과, 0.3 은 과부하 점검 |
| seed | 0 ~ 4 | 9주차와 동일 (짝지은 비교) |
| 정책 | 기존 5종 + `watermark_offload` + `pin_all_capped` = 7종 | 설정당 9 × 7 × 5 = 315 runs |
| 시스템 · 정책 파라미터 | `system_1080ti_llama3b.json`, `policies_week7.json` (새 정책은 기본값 상한 0.9) | 9주차와 동일 |
| 판정 | 현행 SLO 그대로: normal P95 TTFT ≤ 같은 정책 W0 의 3배 · 거절률 ≤ 10 % · 최고 점유율 ≤ 90 %, seed 별 | 기준을 바꾸지 않는다 |
| 함께 보고 | 90 % 초과 시간 비율, 전송 GiB / run, 재계산 토큰 / run, stress 완료율, normal P95 TTFT 절대값 | 비용과 절대 지연 |

**성공 판정 (실험 전에 정함).**

- H 성립: 180 s · 0.2 에서 `watermark_offload` 의 SLO 통과 seed 수가 **모든 조건에서 Evict/Recompute 이상**이고, 재계산 0, normal P95 TTFT 가 Evict/Recompute 이하.
- 부분 성립: 통과 수는 Evict 이상이지만 TTFT 가 Evict 보다 길다 → 상한 강제의 비용이 지연으로 나타남.
- 불성립: 통과 수가 Evict 보다 적다 → 실패 원인(거절 · TTFT)을 seed 별로 분해해 보고.
- 대조: `pin_all_capped` 가 `watermark_offload` 보다 TTFT · 거절이 나쁘면 "회수가 필요하다"를 뒷받침.

## 5. 하지 않는 것

- 판정 기준 · 워크로드 · 설정 변경 (팀원 담당, 9주차 그대로)
- 상한 값 튜닝 (0.9 고정. 다른 값은 별도 실험으로 기록)
- 실제 GPU 실측 (G4, 별도)
- Duration-Aware 에 상한을 붙인 변형 (결과를 본 뒤 필요하면 별도 계획)
