# Watermark 입장 상한 민감도 실험 계획

작성: 2026-11-03. 기준 커밋은 `80404dc`다. 기존 `week10_experiment.md`의 후속 항목인 80%·85%·95%를 실행하며, 90%는 기존 제안값, 100%는 LRU와의 동일 동작 검증점으로 포함한다. 아래 조건은 본 실험 결과를 확인하기 전에 정한다.

## 질문과 예상

입장 상한을 낮추면 GPU 여유를 확보하는 대신 어떤 전송·지연·거절 비용이 발생하는가? 상한을 내릴수록 매번 전송이나 지연이 단조 증가한다고 가정하지 않는다. 입장과 복귀 시각이 달라지며 결과가 비선형으로 달라질 수 있다.

이번 실험은 상한의 민감도를 설명하는 실험이다. 결과를 보고 기존 기본값 0.9를 변경하거나 최적 상한을 확정하지 않는다. Duration-Aware의 파라미터·PCIe·CPU 크기는 변경하지 않는다.

## 고정 조건

| 항목 | 값 |
|---|---|
| Watermark 입장 상한 | 0.80, 0.85, 0.90, 0.95, 1.00 |
| 기준 정책 | `lru_offload`, 기본 설정 |
| 입력 설정 | `week7.json`(60초·0.2/s), `week7_180s_stress02.json`, `week7_180s_stress03.json` |
| 워크로드 | 기존 9조건 전체: W0, base·burst·wait·both의 2x·4x |
| seed | 0~14, 정책·상한 간 동일 trace를 사용하는 짝지은 비교 |
| 시스템 | `system_1080ti_llama3b.json`, GPU 4GiB·CPU 64GiB·PCIe 12GB/s |
| 나머지 정책값 | `policies_week7.json` 그대로 |
| 규모 | 3설정 × 9조건 × 15 seed × (5상한 + LRU) = 2,430 runs |
| 주 설정 | 180초·0.2/s. 60초는 초기·버스트 진단, 180초·0.3/s는 과부하 점검 |

seed 0~14는 기존 분석에서도 사용한 seed다. 새로운 최종 평가 표본이나 파라미터 선택과 분리된 홀드아웃이라고 부르지 않는다. 값 선택을 후속으로 수행한다면 선택 규칙을 별도 기록하고 새로운 seed에서 평가한다.

## 평가 지표와 해석

- 기존 SLO: 각 **상한·같은 seed의 W0** 대비 normal P95 TTFT ≤ 3배, normal 거절률 ≤ 10%, Peak ≤ 90%. 상한이 달라도 이 평가 기준은 변경하지 않는다.
- 절대 normal P95 TTFT, normal 입장 대기 P95, normal 거절률, stress 완료 수·완료율.
- Peak의 seed 평균·최댓값, 평균 점유율, 90% 초과 시간 비율.
- 전송 GiB/run, 재계산 tokens/run, offload·reload 횟수.
- 실제 도구 종료부터 다음 첫 토큰까지 복귀 P95. 원본 `TOOL_END`와 다음 턴 `FIRST_TOKEN`을 연결해 offload 잔여 대기를 포함한다. 기존 엔진·요청 도착 시각·입장 마감 시각은 수정하지 않는다.
- 각 지표는 seed별 run 지표를 먼저 구한다. 전체 요청을 합친 P95나 여러 구간 P95의 합으로 해석하지 않는다. 9조건 평균과 대표 `both_4x`를 구분한다.
- 상한 90% 대비 차이는 동일 조건·seed끼리 구한다. 보조 불확실성 표시는 각 seed의 9조건 평균 차이를 계산한 후 seed 15개를 2,000회 bootstrap 재표집한 95% 구간이다. 135회를 독립 표본으로 취급하지 않으며 유의성 검정이나 최적값 선택 기준으로 쓰지 않는다.
- 비용 누계는 warm-up·drain 포함 전체 run이고, 요청 지표는 warm-up 이후다. 서로 다른 기간의 전송 총량만으로 효율을 비교하지 않는다.
- 95%·100% 변형은 평가 목표인 Peak 90%를 넘을 수 있다. 전체 SLO 통과 수만으로 상한의 성능 순위를 정하지 않고 절대 성능과 메모리 여유·비용을 함께 보고한다.
- 완료 요청만의 지연은 거절·완료 수와 함께 보고한다. 복귀 지연은 첫 턴을 제외하고 실제 도구 종료가 warm-up 이후인 완료 stress 복귀 턴을 대상으로 한다.

## 검증과 보존

1. 각 상한의 모든 occupancy sample이 `floor(상한 × 전체 blocks)` 이하인지 검사한다.
2. 상한 1.0의 Watermark와 LRU가 405개 짝지은 run에서 정책 이름·설정·run 식별자 외 기존 요약값 및 requests·occupancy·events가 같은지 확인한다.
3. LRU의 seed 0~4는 로컬에 보존된 9주차 135회 결과와 대조한다.
4. 각 상한의 W0 상대 지연과 SLO를 기존 집계 함수로 계산한다.
5. 입력 해시, 시스템·정책 설정, seed, 실행 코드 해시를 보존하고, 기존 결과 폴더를 덮어쓰지 않는다.

실험 결과는 별도 `week10_watermark_ceiling.md`에 기록한다. 기존 90% 제안 정책의 계획·결과 문서는 유지한다.
