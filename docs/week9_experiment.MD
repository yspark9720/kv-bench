# 9주차 실험: 기간·stress 도착률에 따른 KV 정책 비교

작성 기준: 2026-10-27. 현재 코드와 저장된 `experiment.json`, `summary.csv`, `comparison.csv`, `slo_by_seed.csv`, run별 요청·점유율·이벤트를 대조한 기록이다.

## 1. 목적과 현재 확인한 차이

연구 질문은 **도구를 기다리는 Agent 세션의 KV를 언제 유지·이동·삭제해야 일반 요청 SLO를 지키면서 재계산·전송 부담을 줄일 수 있는가**다. 기존 다섯 정책을 바꾸지 않고 W2의 버스트와 교대 대기를 분리한 뒤, 입력 기간과 stress 도착률을 바꿔 비교했다.

관측된 정책별 차이는 다음과 같다.

- **Pin-All:** 낮은 부하에서는 복구 비용이 없지만, 부하가 커지면 idle KV 보유가 일반 요청의 긴 대기·거절과 낮은 stress 완료율로 이어진다.
- **Evict/Recompute:** 메모리 여유와 현행 SLO 통과에서 강하지만 재계산이 늘어난다.
- **Fixed TTL:** 일부 조건에서는 재계산을 줄이면서도 통과하지만, 고정 3초 기준의 효과가 도착 밀도와 도구 대기에 민감하다.
- **LRU Offload:** 재계산 없이 짧은 normal TTFT를 유지하지만 GPU가 높은 점유율에 머무르는 시간이 길다.
- **Duration-Aware:** LRU보다 전송을 더 사용하면서 90% 초과 시간을 줄인다. TTFT 차이는 작고 순간 Peak 목표는 여전히 놓친다.

이는 seed 5개에서 관측한 **성능·비용 측면의 차이**다. 통계적 유의성을 검정한 결과가 아니며, 모든 조건에서 가장 좋은 정책을 확정하지 않는다.

## 3. 지표를 읽는 기준

현행 SLO는 seed마다 아래 세 기준을 모두 만족해야 통과한다.

1. normal P95 TTFT ≤ **해당 정책·같은 seed의 W0 P95 × 3**
2. normal 거절률 ≤ 10%
3. Peak KV 점유율 ≤ 90%

| 지표 | 집계 범위·의미 |
|---|---|
| normal P95 TTFT·거절률 | warm-up 이후 도착한 normal 요청. TTFT는 완료 요청만 집계 |
| stress 완료시간·완료율 | warm-up 이후 최초 도착한 stress 세션. 시간은 완료 작업만 집계하고, 완료율은 제출·완료 수도 함께 사용 |
| Peak KV | warm-up 이후 drain 종료까지의 순간 최댓값 |
| 평균 KV·90% 초과 비율 | `[warmup_ms, duration_ms)`의 시간 가중 값 |
| 전송·재계산·정책 동작 횟수 | warm-up과 drain을 포함한 전체 run 누계 |
| 현재 per-job 비용 | 위 전체 누계 ÷ warm-up 이후 도착해 완료한 작업 수. 엄밀한 효율 비교 전 집계 범위를 맞춰야 함 |
| 처리량·서버 busy 비율 | drain을 포함한 종료 시각이 분모에 들어가므로 입력 기간·도구 대기 규칙의 영향도 받음 |

이 문서의 TTFT·Peak·거절률·초과 비율·비용 표는 **seed별 run 지표를 평균**한 값이다. 전체 요청을 합친 P95가 아니고, 평균 Peak가 90% 미만이어도 일부 seed가 실패할 수 있다. stress 완료율 표는 다섯 seed의 완료 수 합계 ÷ 제출 수 합계다. 재계산 단위 `천 토큰`과 전송 단위 `GiB`는 서로 다른 비용이므로 직접 합산하지 않는다. 기간이 다른 실험의 총 전송·재계산을 그대로 효율 순위로 비교하지 않는다.

90%는 평가에서 정한 여유 공간 목표이며, 현재 엔진은 풀 용량 100% 안에서 입장을 허용한다. 상대 TTFT SLO는 정책마다 W0 기준이 다르므로 정책 간 절대 성능 순위와 일치하지 않을 수 있다. 결과가 나쁜 정책의 거절로 TTFT 표본도 달라질 수 있어, 지연·거절·완료 수를 함께 읽는다. 자세한 정의는 [시뮬레이터](simulator.md#지표)에 있다.

## 6. 정책별로 얻을 수 있는 의미 있는 차이

### Pin-All: idle KV 관리가 필요한 이유를 보여주는 기준선

W0가 가벼운 60초·0.2에서는 normal TTFT가 짧고 복구 비용이 없다. 하지만 W2 4x에서는 normal P95가 약 13.7초에서 29.9초 수준으로 커지고 거절도 늘어난다. stress 완료율은 84.91% → 47.24% → 29.75%로 낮아진다. 계속 보유하는 KV가 다른 요청의 입장에 영향을 준다는 프로젝트의 문제 설정을 뒷받침한다.

180초 W2의 P95가 입장 제한 30초 근처에 머무는 것은 안정성의 증거가 아니다. 늦은 요청의 거절과 완료 요청만의 TTFT 집계가 함께 작용하므로, 더 강한 부하에서도 처리 능력이 같다고 읽지 않는다.

### Evict/Recompute: 메모리 확보와 재계산 부담의 기준선

대표 W2 4x에서 평균 Peak는 58.63% → 80.91% → 93.80%로 다섯 정책 중 가장 낮고 SLO 통과는 5/5 → 4/5 → 1/5다. 대신 약 12.6만 → 36.1만 → 52.3만 토큰을 run마다 재계산한다. 재계산은 공유 prefill 서버도 사용하므로 일반 요청의 대기에 영향을 줄 수 있다.

새 정책의 비교 질문은 이 정책의 메모리 여유를 어느 정도 유지하면서 지연·재계산 부담을 줄일 수 있는가다. 다만 0.3의 W0에서도 즉시 idle 삭제만으로 Peak를 모두 지키지는 못했다. active KV 예약, prefill 대기와 입장 방식을 추가 확인할 근거이며, 현재 결과만으로 모든 idle 정책의 한계를 증명한 것은 아니다.

### Fixed TTL: 고정 대기 기준의 절충 효과와 부하 민감도

60초·0.2 W2 4x에서는 Evict/Recompute와 같은 5/5 통과에 재계산 약 28% 감소, normal P95도 약 10% 짧다. 180초·0.2에서는 재계산·P95가 더 작지만 통과가 2/5로 줄어든다. 180초·0.3에서는 normal P95가 Evict/Recompute보다 약 71% 길다.

TTL 3초의 효과는 세션 유입과 복귀 시각, 대기 규칙에 따라 달라진다. 긴 대기는 TTL이 만료돼 KV를 비울 기회도 주므로 4x에서 일부 지표가 좋아질 수 있다. 고정 TTL의 약점을 확인한 것이며 아직 적응형 TTL의 우위를 입증한 결과는 아니다.

### LRU Offload: 낮은 지연과 긴 과밀 지속시간

대표 조건에서 재계산·normal 거절은 0이고 TTFT도 짧다. 하지만 block이 부족할 때 회수하는 현재 구현은 평가 기준인 90%를 넘는 시간이 길다. 지연이 짧다는 장점과 GPU 여유 공간을 유지하지 못한다는 약점을 함께 보고해야 한다.

### Duration-Aware: 더 많은 전송으로 과밀한 시간을 줄임

| 설정 | LRU 90% 초과 비율 (%) | Duration-Aware 90% 초과 비율 (%) | LRU 전송 (GiB) | Duration-Aware 전송 (GiB) |
| --- | --- | --- | --- | --- |
| 60초·0.2 | 15.79 | 1.13 | 2.60 | 5.93 |
| 180초·0.2 | 32.06 | 3.59 | 22.73 | 37.13 |
| 180초·0.3 | 38.02 | 6.88 | 46.15 | 65.00 |

세 설정 모두 LRU보다 전송을 더 쓰면서 90% 초과 비율을 크게 낮춘다. W2 2x·4x에서 같은 seed끼리 비교해도 모두 같은 방향이었다. 그러나 대표 조건의 normal P95 차이는 각각 0ms, 약 3ms, 약 19ms여서 “응답이 훨씬 빨라졌다”는 설명은 맞지 않는다. 주요 차이는 메모리 여유의 지속성과 전송 비용에 있다.

Duration-Aware도 순간 Peak는 높아 180초의 `both`에서는 전체 통과가 0/5다. 실제 미래 대기시간을 알면서도 Peak를 놓치므로, 예측 정확도와 회수·입장 시점의 제어를 별도로 검증해야 한다.

## 7. 원인을 좁히는 추가 진단

### 행동 선택 범위

| 설정 | 조건 | idle KEEP | idle OFFLOAD | idle EVICT | 전체 EVICT 이벤트 |
| --- | --- | --- | --- | --- | --- |
| 60초·0.2 | both_2x | 140 | 41 | 0 | 0 |
| 60초·0.2 | both_4x | 142 | 39 | 0 | 0 |
| 180초·0.2 | both_2x | 329 | 187 | 0 | 0 |
| 180초·0.2 | both_4x | 287 | 229 | 0 | 0 |
| 180초·0.3 | both_2x | 374 | 382 | 0 | 0 |
| 180초·0.3 | both_4x | 387 | 369 | 0 | 0 |

KEEP/OFFLOAD/EVICT는 idle 진입 시 결정의 다섯 seed 합계다. pressure offload는 별도로 실행될 수 있어 idle OFFLOAD 수가 전체 offload 횟수는 아니다. 실제 EVICT 이벤트도 모두 0이었다. CPU 64GiB와 빠른 PCIe 가정에서 주로 KEEP/OFFLOAD만 시험한 결과이므로 3-way 최적 선택의 성능이라고 주장할 수 없다. 현재 선택식은 대기와 전송 비용·CPU 여유를 쓰며 로그의 재계산 추정값을 직접 최적화하지 않는다. oracle 입력도 휴리스틱의 최적성을 보장하지 않는다.

### Peak 근처의 회수와 입장

| 설정 | 선택한 Duration-Aware W2 4x 사례 | 관측 |
|---|---|---|
| 60초·0.2 | seed 2, 30.991초, Peak 97.78% | stress ADMIT들이 먼저 점유율을 올리고, 근처의 다음 idle offload는 31.387초에 시작 |
| 180초·0.2 | seed 1, 130.617초, Peak 99.96% | 앞선 offload가 끝난 뒤 새 입장이 여유를 다시 소진하고 추가 pressure offload가 뒤따름 |
| 180초·0.3 | seed 4, 168.645초, Peak 100% | offload 완료와 같은 시각의 stress ADMIT에서 풀 용량에 도달 |

각 설정의 가장 높은 Peak seed 한 사례를 본 것이다. 모든 실패를 같은 원인으로 단정할 수는 없다. 다음에는 Peak 당시 active·idle·전송 중 KV의 소유량을 기록해 회수할 KV가 없었는지, 회수가 늦었는지, 회수 후 입장이 여유를 소진했는지를 구분해야 한다.

### 도구 대기를 제외한 stress 작업시간

노트북 9절은 완료한 작업마다 아래 값을 계산한 뒤 run별 P95와 seed 평균을 구한다.

```text
도구 대기 제외 작업시간
  = 마지막 턴 완료 시각 - 최초 외부 도착 시각 - 해당 작업의 도구 대기시간 합
```

두 집단의 P95끼리 빼는 방식이 아니다. 이 값에도 decode·prefill·입장 대기·재계산·reload가 들어가므로 KV 정책만의 순수 비용은 아니다.

| W2 4x 설정 | Duration-Aware P95 평균 (초) | Evict/Recompute P95 평균 (초) |
| --- | --- | --- |
| 60초·0.2 | 15.98 | 17.93 |
| 180초·0.2 | 16.43 | 18.55 |
| 180초·0.3 | 17.10 | 19.05 |

원래 stress 완료시간은 긴 도구 대기에 좌우돼 정책 차이가 가려질 수 있다. 보조 지표로 모델·스케줄링 구간도 확인하되, 완료율이 다른 정책에는 살아남은 작업만 남는 표본 차이가 있으므로 완료 수를 함께 비교한다. 이 분석은 기존 `summary.csv`를 변경하지 않고 요청 기록과 입력 trace로 재구성했다.

### Peak 집계 구간의 민감도

전체 675회에서 Peak를 `[warmup_ms, duration_ms)`로 제한하는 보조 판정을 확인하면 전체 SLO가 바뀌는 실행은 다음 한 번이다.

| 설정 | 조건 | 정책 | seed | 기존 Peak (%) | 입력 구간 Peak (%) | 기존 SLO | 입력 구간 SLO |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 180초·0.3 | wait_2x | Fixed TTL | 0 | 93.80 | 82.22 | 실패 | 통과 |

이때 `wait_2x` Fixed TTL의 180초·0.3 통과 수는 현행 0/5에서 보조 판정 1/5가 된다. 나머지 전체 SLO 판정은 같다. 원본 SLO와 CSV는 유지했다. 문서의 모든 통과 수는 현행 정의를 따른다.

## 8. 프로젝트 방향과 다음 확인 순서

| 설정 | 이번 분석에서의 역할 |
|---|---|
| 60초·0.2 | 정책 차이와 실패 원인을 드러내는 초기 진단. 장시간 안전성의 근거로 확대하지 않음 |
| 180초·0.2 | 장시간 부하·입장과 Peak 제어를 점검하는 주 실험 후보. W0도 일부 경계에 있음 |
| 180초·0.3 | 과부하에서 지연·거절·완료 수와 비용이 어떻게 변하는지 보는 시험 |

프로젝트의 기여는 통제된 워크로드에서 정책의 지연·메모리·복구 비용 차이를 재현하고, 개선할 실패 원인을 좁히는 데 있다. 다음 개선안을 평가할 때는 **같은 일반 요청 SLO 아래에서 메모리 여유와 재계산·전송 비용이 어떻게 달라졌는가**를 설명해야 한다.

다음 항목은 아직 실행하지 않은 후속 계획이다.

1. **평가 기준과 집계 범위를 먼저 고정한다.** 기존 SLO를 보존하고, 서비스 요구에 근거한 절대 normal TTFT·stress 완료율 목표를 정한다. Peak와 초과 지속시간 중 무엇이 엄격한 운영 제약인지 사전에 결정하고 비용의 분자·분모 구간을 맞춘다. 실패를 없애기 위해 사후에 기준을 바꾸지 않는다.
2. **Peak의 KV 소유 상태와 지연을 분해한다.** active·idle·전송 중 KV, 입장 대기열과 PCIe 대기를 확인한다. 대기시간 예측이 맞아도 실패하는 이유와 회수·입장 시점의 효과를 분리한다.
3. **운영 가능한 구간을 찾는다.** 같은 시스템에서 기간·stress 도착률·GPU 풀 크기를 통제해 비교한다. 예를 들어 도착률 0.10·0.15·0.20·0.25·0.30을 같은 기간·정책·평가 seed로 훑을 수 있다. 한 정책이 통과할 때까지 조건을 따로 조정하지 않는다.
4. **미검증된 선택 범위와 가정을 시험한다.** 평균을 맞춘 대기 분포, 작은 CPU 풀, 느린 PCIe, 대기 예측 오차를 별도 실험으로 두고 EVICT까지 실제 실행되는지 확인한다. 파라미터 선택 seed와 최종 평가 seed를 구분하고 seed 수와 불확실성 보고를 늘린다.
5. **실제 대상 환경과 연결한다.** prefill·decode·KV 크기·전송 속도를 보정하고 민감도를 확인한다. 현재의 고정 decode 속도·단일 FIFO prefill/PCIe 결과를 실제 GPU 절대 성능으로 주장하지 않는다.

새 정책·입장 제어의 구현과 실측 성능 검증은 후속 작업이다. 이 문서의 결과만으로 완성된 최적 정책, 현실 예측기 성능, 통계적 유의성을 입증했다고 표현하지 않는다.

## 9. 재현 방법과 결과 보존

프로젝트 루트에서 아래처럼 **새 출력 경로**를 사용한다. 현재 리뷰 노트북은 2절의 보존된 결과를 읽으므로, 새 결과를 노트북에서 검토하려면 해당 노트북의 `OUTPUT`을 새 경로로 바꾼다. 실행기는 기존 출력 폴더가 있으면 종료한다. 이벤트를 사용하는 노트북을 위해 `--no-events`는 넣지 않는다.

```powershell
python -m kvbench w2-factorial --config configs/week7.json --system configs/system_1080ti_llama3b.json --policies configs/policies_week7.json --output results/week9_60s_stress02_replay
python -m kvbench w2-factorial --config configs/week7_180s_stress02.json --system configs/system_1080ti_llama3b.json --policies configs/policies_week7.json --output results/week9_180s_stress02_replay
python -m kvbench w2-factorial --config configs/week7_180s_stress03.json --system configs/system_1080ti_llama3b.json --policies configs/policies_week7.json --output results/week9_180s_stress03_replay
```

설정당 `experiment.json`, trace 45개와 메타데이터, run 225개의 summary·requests·occupancy·events, 전체 `summary.csv` 225행, `comparison.csv` 45행, `slo_by_seed.csv` 225행을 확인한다. 같은 seed의 재실행은 재현 확인이며 표본 추가가 아니다. 정책·시스템 파라미터를 바꾼 실행은 별도 실험으로 기록한다.

전체 실험 구조는 [W2 요인 분리](w2_diagnostics.md), 이전 45회 실험은 [7주차 문서](week7_experiment.md), 지표 구현은 [metrics.py](../kvbench/metrics.py), 정책 구현은 [policies 폴더](../kvbench/policies)에 있다.
